# Paperflow

Автоматизированный конвейер обработки документов для
[Paperless-ngx](https://docs.paperless-ngx.com/): скан, письмо с вложением или ручная загрузка
проходят OCR, классифицируются LLM (заголовок / отправитель / тип документа / теги / кому из
домохозяйства принадлежит) и проверяются на наличие срока (дедлайн, срок ответа, срок оплаты) —
с опциональным напоминанием в Google Tasks. Всё попадает в Paperless с уже заполненными
метаданными — раскладывать руками нечего.

Этот файл — вводная для того, кто (человек или ИИ-агент) продолжит работу над проектом без
предыдущего контекста: что тут есть, зачем, как это всё связано, и на какие грабли уже
наступали, чтобы не наступать снова.

## Зачем

Домохозяйство, получающее регулярный поток официальной почты (госучреждения, банки, страховые,
арендодатель) более чем на одном языке, в итоге получает либо коробку бумаг, либо
полу-разобранное дерево папок — ни то ни другое не масштабируется и не ищется по содержимому.
Paperless-ngx решает хранение и полнотекстовый поиск, но сам по себе не умеет: (а) надёжно
распознавать смешанный по языку или рукописный текст на посредственном скане, (б) понимать, что
именно за письмо и от кого, чтобы его прилично подписать, (в) заметить, что в письме есть срок.
Этот проект — тот самый слой, который делает эти три вещи.

## Два пакета

Конвейер разделён на переиспользуемый движок и Paperless-специфичную привязку — намеренно:
движок ничего не знает о Paperless, поэтому другое хранилище документов могло бы переиспользовать
его без переписывания. Граница физическая, а не договорённость, которую можно случайно
нарушить — `docflow` не зависит от `paperflow`, поэтому случайный обратный импорт просто не
соберётся.

```
packages/
  docflow-core/   ← движок: открыть PDF, OCR/эскалация/классификация/извлечение срока,
                     ничего не пишет и никуда не ходит, кроме LLM-шлюза и файла на диске
  paperflow/      ← привязка к Paperless-ngx + приложения (вотчер, вебхук-сервис, CLI)
```

`docflow` возвращает всё **именами** (`DocumentClassification(title, correspondent, ...)`),
никогда не id Paperless — разрешение имени в id, и решение о том, что уже существует, а что нужно
создать, целиком забота `paperflow`. Именно это решение делает движок переносимым: реализовать
`docflow.ports.taxonomy.TaxonomySource` для другого менеджера документов — пара десятков строк,
а не переписывание.

```
src/docflow/
  domain/  ports/  adapters/{pdf,ocr,llm}/  llm_tasks/  pipeline/

src/paperflow/
  domain/  adapters/{paperless,google,windows}/  pipeline/  i18n/
  apps/  service/  watcher/  cli/
```

## Как обрабатывается документ

```
скан / email / веб-загрузка
        │
        ▼
Workflow Paperless "Document Added" (без фильтра по источнику) ──► вебхук
        │                                                             │
        ▼                                                             ▼
  (ночная страховка на случай,                              вебхук-сервис paperflow
   если вебхук был недоступен                                 (FastAPI, один документ
   в момент добавления документа)                              за раз — RapidOCR/LLM-шлюз
                                                                 не рассчитаны на
                                                                 конкурентные вызовы)
                                                                        │
                                                                        ▼
                                                  скачать → OCR-каскад → классификация →
                                                  PATCH обратно в Paperless → извлечь срок →
                                                  PATCH + опциональное напоминание
```

Внутри OCR-каскада, постранично:

```
born-digital? (есть текстовый слой, и страница не является в основном картинкой-сканом)
  ├─ да  ──► текстовый слой берётся как есть, OCR не нужен
  └─ нет ──► RapidOCR (две языковые модели) ──► достаточно хорошо? ──► готово
                                                       │
                                                       нет
                                                       ▼
                                    эскалация: рендер страницы, запрос к vision-LLM
```

Единственный Docker-сервис (`docker/service.Dockerfile`) — единственное место, где этот каскад
выполняется. Вотчер и ночная страховка тонкие: они лишь сообщают Paperless «документ существует»
— один и тот же вебхук одинаково обрабатывает скан, email-импорт и ручную загрузку.

## Приложения

- **`paperflow.apps.watcher`** — работает непрерывно рядом с физическим сканером. Следит за
  папкой, загружает новые файлы в Paperless без метаданных (они придут позже, асинхронно, из
  вебхук-сервиса), хранит локальную копию, отправляет уведомление на рабочий стол.
- **`paperflow.apps.service`** — тот самый FastAPI вебхук-сервис. Единственная
  контейнеризованная часть системы.
- **`paperflow.apps.cli`** — четыре небольших инструмента: ночная страховка-триггер
  (`paperflow-trigger`, подбирает документы, пропущенные вебхуком), поиск дублей документов по
  сходству OCR-текста и perceptual hash, а не по побайтовому совпадению (`paperflow-duplicates`),
  утилита раскраски тегов Paperless (`paperflow-tag-colors`) и одноразовый OAuth-флоу Google
  (`paperflow-google-auth`).

Вывод CLI и вотчера локализован (`ru`/`en`, через `paperflow.i18n`); лог-записи всегда на
английском — это гарантировано правилом ruff, не запрещающим `paperflow.i18n` вне слоя приложений.

## Конфигурация

Всё читается из переменных окружения (замороженные dataclass'ы, `Settings.load(profile)` для
`"watcher"` / `"service"` / `"cli"` — каждый профиль требует только то, что реально использует).
Скопируй `.env.example` в `.env` и заполни — там полный список переменных с описанием. Ни у
одного секрета или хоста нет дефолта в коде — недостающая переменная даёт один `ConfigError`,
перечисляющий все проблемы разом, а не 401 посреди обработки документа.

`family_members.example.json` описывает единственный кусок локальной конфигурации вне переменных
окружения: JSON-список того, на кого из домохозяйства подписываются документы в архиве.

## Внешние сервисы

Проект ничего не считает «сам» в облаке — он обращается к self-hosted инстансу Paperless-ngx,
self-hosted прокси LiteLLM (перед одним или несколькими провайдерами моделей) и, для напоминаний,
к Google Tasks. Форму этой конфигурации см. в `.env.example`; ни один адрес не зашит в код внутри
`packages/`.

Через прокси идут независимые LLM-задачи с разными моделями и разными бюджетами квоты, чтобы
тяжёлый день OCR-эскалации не мог заморить классификацию (и наоборот): постраничная эскалация
транскрипции использует более крупную vision-модель, а извлечение срока и классификация — более
быстрые и дешёвые модели. Какая модель отвечает за какую задачу — целиком настройка `.env`
(`VISION_PROXY_MODEL`, `FRIST_LLM_MODEL`, `CLASSIFIER_LLM_MODEL`).

## Разработка

```bash
pip install -e ./packages/docflow-core -e "./packages/paperflow[service,dev]"
ruff check .
mypy packages/docflow-core/src packages/paperflow/src
pytest
```

`experiments/` содержит одноразовые диагностические скрипты (сравнение OCR-бэкендов, калибровка
порогов эскалации и т.п.) — не тесты, не подчиняются стандартам остального репозитория, не
обязаны работать без правок по мере изменения окружающего кода. См. `experiments/README.md`.

## Docker

Вебхук-сервис — единственная контейнеризованная часть:

```bash
docker build -f docker/service.Dockerfile -t paperflow-service .
```

Реальная граблина при сборке, которую стоит знать заранее: `rapidocr` тянет `opencv-python` (не
headless-сборку), а той при импорте нужны системные графические библиотеки, которых нет в
минимальном `python:3.11-slim`. Без них импорт падает с `ImportError: libxcb.so.1: cannot open
shared object file` — а поскольку fallback OCR-адаптера ловит именно `ImportError`, реальная
причина маскируется под не связанный с ней `ModuleNotFoundError`. Чинится установкой `libgl1
libglib2.0-0 libsm6 libxext6 libxrender1` до `pip install` (см. Dockerfile).

Ни `credentials/` (OAuth-токен Google), ни `family_members.json` не запекаются в образ — оба
файла несут данные, которым нечего делать в слое образа, поэтому оба монтируются во время
запуска. Монтирование credentials **не** должно быть read-only: токен перезаписывается при
рефреше примерно раз в час, и read-only том превращает это в тихий сбой — напоминания продолжают
работать вплоть до первого истечения токена и затем перестают, без единой видимой ошибки, кроме
самой попытки рефреша.

## Грабли, на которые уже наступали

Коротко здесь; подробное обоснование — в комментариях/докстрингах соответствующего модуля.

1. **Зависший HTTP-шлюз неотличим от медленного.** `timeout=` в `requests` меряет паузы МЕЖДУ
   байтами, а не общее время ожидания — прокси, который держит соединение открытым
   (keep-alive/трикл байтов) без завершения ответа, обходит эту защиту полностью. Фикс — жёсткий
   wall-clock дедлайн со стороны клиента через фоновый пул потоков, не зависящий от того, что
   происходит на уровне сокета.

2. **Vision-LLM может зациклиться на генерации**, не дойдя до стоп-токена — конкретно на длинных
   визуально повторяющихся элементах без реального текстового содержимого (штрихкоды, QR-коды,
   пустые поля для подписи). При `temperature=0` сбежать из локального цикла нечем. Настоящий
   фикс — не `max_tokens`/`frequency_penalty` (это лишь ограничивает ущерб), а явный пункт в
   промпте: не транскрибировать такие элементы посимвольно, обозначать короткой пометкой, плюс
   правило не повторять один символ подряд больше нескольких раз.

3. **PATCH `custom_fields` на этом сервере Paperless заменяет весь список целиком, а не
   дополняет его** — подтверждено эмпирически, а не чтением исходников сервера (которые для
   большинства типов полей описывают более безопасное поведение по умолчанию). Реальный документ
   потерял все поля, записанные более ранним шагом, когда более поздний PATCH их перезаписал.
   Фикс — всегда цикл GET → merge → PATCH вместо голого частичного PATCH, в одном месте.

4. **Не все PDF — PDF с первого байта.** Некоторые банковские выписки приходят обёрнутыми в
   PKCS#7/CMS-контейнер электронной подписи, реальный PDF начинается с ненулевого смещения.
   Определяется и распаковывается поиском `%PDF-`/`%%EOF` внутри файла перед передачей в
   Paperless.

5. **Полностраничный perceptual hash плохо различает официальные письма от одного отправителя**,
   использующие общий шаблон/шапку, но разные по содержанию — наивная транзитивная кластеризация
   («A похож на B, B на C → все трое одна группа») усугубляла проблему, склеивая несвязанные
   письма. Фикс — основной сигнал для поиска дублей — сходство OCR-текста (шинглы + коэффициент
   Жаккара), perceptual hash — запасной путь только для документов почти без текста (сканы
   паспортов, фото), результат — пары с показанным числом схожести, а не транзитивные группы.

6. **Консоль Windows не кодирует не-ASCII вывод по умолчанию** — голый `print()`/
   `logging.StreamHandler()` падает с `UnicodeEncodeError`, как только локализованный текст
   попадает в терминал со старой кодовой страницей. Фикс — один раз, централизованно,
   переконфигурировать stdout в UTF-8 до какого-либо логирования.

7. **Необработанное исключение под `pythonw.exe` (без консоли, например Task Scheduler
   `LogonTrigger`) абсолютно невидимо** — ни traceback'а, ни следа, просто тихо умерший процесс.
   Фикс — `sys.excepthook`/`threading.excepthook`, установленные при старте, гарантируют запись
   traceback'а в лог до смерти процесса — и в вотчере, и в воркер-потоке сервиса.

8. **`LogonTrigger` не гарантирует немедленный запуск при логоне** — сетевые сервисы, от которых
   зависит задача, тоже могут быть ещё не подняты. Небольшая задержка старта плюс частое
   повторение с политикой «игнорировать новый экземпляр, если один уже запущен» делают задачу
   самовосстанавливающейся: если процесс жив, повторные срабатывания — no-op; если умер по любой
   причине — следующее повторение перезапустит его в течение нескольких минут.

9. **Тело JSON вебхука воркфлоу может быть закодировано дважды** — если действие настроено с
   телом-шаблоном, некоторые версии Paperless-ngx рендерят шаблон в готовую JSON-строку и передают
   её как значение параметра запроса `json=`, который кодирует её ЕЩЁ РАЗ. Тело оказывается
   JSON-строкой, содержащей JSON, а не самим объектом. Фикс — определять эту форму после первого
   разбора и парсить ещё раз, вместо того чтобы полагаться на точную комбинацию настроек в
   конкретной версии сервера.

10. **Плейсхолдер id документа в шаблоне тела вебхука не всегда называется так, как ожидаешь** —
    и доступен только на триггере «документ добавлен», не на более раннем «начата обработка»,
    где документа ещё нет в базе. Проверяй реальные переменные шаблона своей версии Paperless-ngx,
    а не полагайся на предположение.

11. **Docker network alias, заданный на одной сети, не виден на другой сети того же
    контейнера.** Если сервис резолвится по внутреннему имени из одного контейнера, но получает
    connection refused из другого контейнера на другой Docker-сети — проверь, не объявлен ли
    alias только в блоке первой сети.
